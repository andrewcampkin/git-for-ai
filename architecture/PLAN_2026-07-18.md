# Plan Update — 2026-07-18

Supersedes the *sequencing* in [`CLI_PLAN.md`](./CLI_PLAN.md) (whose per-milestone specs remain
authoritative unless amended here) and extends [`MONOREPO_PLAN.md`](./MONOREPO_PLAN.md) with a
review of the non-CLI surfaces. Written after dogfooding surfaced real issues, and after the
project owner sharpened the vision statement:

> The system is a source control layer **for AI agents to use** — the features beyond standard
> git are for agents adding richer information and capturing context that assists agents — **and**
> it must *prove* it's working to a human user, giving them a way to review what their agents did.

That second clause is new relative to the original docs and changes some priorities below.

### 1.2 Defects to fix

**D1 — R4 inferred-continuation uses the wrong similarity signal.**
`resolve.ts`'s R4 branch treats "≥70% of the union of both trees' paths carry identical blobs"
as evidence that a commit continues its parent's logical change. But any small commit in a
non-tiny repo leaves most of the tree identical — so R4 fires for essentially *every*
trailerless child of a mapped commit. Live evidence: `8e25afb` (M7) and `7d4cd73` (handoff doc)
— unrelated changes — share change-id `1b4aba46`, and the doc commit's ledger entry now
*supersedes* M7's, so `show 8e25afb` reports the wrong effective intent and buries the 348-span
M7 session. Fix: replace whole-tree similarity with **changed-path overlap** (the commit's
diff-vs-parent paths must substantially overlap the change's previous diff paths), keep the
threshold configurable, and have `doctor` (M14) audit `origin: inferred` rows. R4 matters most
for repos adopting git-for-ai mid-history, which is the normal onboarding path — this must be
right before anyone else onboards a repo.

**D2 — This repo's change-map carries the miswire.** Repair after D1 via the real `relink`
command (§1.4 W1): give `7d4cd73` its own change-id, restore `1b4aba46`'s head/history to
`8e25afb`, and re-point each ledger entry/session where it belongs.

### 1.3 Vision gap: the agent write path

`DATA_MODEL.md` §2.5 defines a rich `reasoning` vocabulary (intent, constraints,
rejected-alternatives, confidence, scope_risk, reversibility, tested, related) — but the only
writer today is passive session capture, which populates `reasoning.intent` alone, and only when
a plan event fired. Nothing lets an agent (or human) deliberately record what it learned.
Two additions, neither requiring schema changes:

- **`git for-ai annotate [<commit|c/change-id>]`** — append a full ledger entry. Primary
  interface: structured JSON on stdin (agent-friendly, validated against
  `ledgerEntrySchema`); secondary: flags for the common fields (`--summary`, `--intent`,
  `--rejected "option::why"`, `--tested`, ...). Defaults to HEAD. Uses the existing
  `resolveChangeId` + `appendLedgerEntry` core APIs. Provenance: a new-to-the-CLI but
  schema-legal value distinguishing deliberate annotation from passive capture.
- **Capture enrichment** — `capture-session` already sees test commands and their outcomes in
  the transcript spans; mine `reasoning.tested` (and plausibly `related`) from what it already
  parses. (Deferred to W4 to keep core churn away from the M9 agent.)

Also: CLI_REFERENCE specifies `show --history` (view superseded entries — exactly what D1's
damage needs for inspection) but M8 didn't implement the flag. Add it with `annotate`.

## Part 2 — Wider-system review (server, online service, desktop, website)

### 2.1 What the existing MONOREPO_PLAN gets right (endorsed, unchanged)

- **CLI-first, everything else wraps `core`** — this held up in practice; keep protecting the
  "core never imports UI/CLI frameworks" rule.
- **The server's differentiated job is shared indexing/query, not ref hosting** (§5.2): ref
  sync is probably free via existing git hosts (W1-#5 validates this cheaply); the expensive
  non-recomputable-everywhere artifact is the embedding index; Postgres + pgvector for the
  shared tier plays to the owner's strongest expertise.
- **Defer accounts/multi-tenant/website** until there's a second real user.

### 2.2 What the new "prove it to the user" requirement changes

The original plan frames the desktop app as "a GUI for `ask`/`blame --why`". The sharpened
vision makes the human surface's real job **agent-activity review**: a place where a user can
see what their agents did, why, with what confidence, and with what evidence. That reframes
priorities in three ways:

1. **A review surface should arrive earlier and cheaper than Electron.** Recommended shape:
   `git for-ai review` — a CLI command that serves a local React SPA (Vite build, static
   assets shipped in the package, reads via `core` in-process; no network, no accounts). The
   `desktop/` package then becomes an Electron *wrapper around the same React app* later, per
   the existing shares-UI-components plan. What it shows, in priority order:
   - **Timeline**: commits × agents × changes, filterable by day/agent/model — "what did my
     agents do this week."
   - **Change detail**: diff side-by-side with the ledger entry — summary, intent, rejected
     alternatives, constraints, `scope_risk`/`reversibility`/`confidence` rendered as visible
     flags, and the **evidence** (`reasoning.tested`, and the session spans showing the tests
     actually running). This is the "prove it" pixel: claim next to evidence.
   - **Session trace viewer**: the captured spans as a readable narrative (what it ran, what it
     edited, what failed and was retried), not raw JSON.
   - **Attention queue**: things `doctor` flags + low-confidence/`inferred`/orphan items —
     review-worthy, not just browsable.
2. **An even cheaper first proof surface**: `git for-ai report [--since <date>] [--md|--html]`
   — a generated digest of agent activity (same data as the timeline, no UI stack). Useful
   immediately for a solo user, trivially shareable, and forces the "what would a human want to
   see" data questions early. Build in W4; it derisks the review UI's information design.
3. **Where users already review is a surface too**: a later GitHub integration that posts the
   ledger entry (summary/intent/rejected/tested) as a PR comment puts the enhanced information
   inside the review workflow humans already trust. Cheap version: `export --format
   pr-comment` piped to `gh pr comment`. App-based automation is product-stage, later.

### 2.3 New recommendation: an MCP server, before the network server

If the primary *consumer* is an AI agent, the highest-leverage integration isn't HTTP — it's
**MCP**. A stdio MCP server exposing `ask`, `blame_why`, `show`, `log_intent`, and `annotate`
as tools makes any MCP-capable agent (Claude Code first) a native reader *and writer* of the
intent layer in whatever repo it's working in — no shell parsing, schema-validated writes.
It's thin (wraps `core` exactly like the CLI does), so it can live as `git for-ai mcp` in the
CLI package initially and move to `server/` if it grows. Recommended slot: immediately after
M12, before sync — it converts the whole system from "a CLI an agent could shell out to" into
"tools an agent natively has," which is the vision's centre.

### 2.4 The four surfaces, updated order

| Order | Surface | Shape | Gate |
|---|---|---|---|
| 1 | **CLI** (Part 1) | complete per §1.4 | in progress |
| 2 | **MCP server** | `git for-ai mcp` (stdio, wraps core) | after M12 |
| 3 | **Review UI** | `git for-ai review` local SPA; `report` precedes it | after M12; `report` can come earlier |
| 4 | **Server** | shared-index tier ONLY (Fastify + pgvector) — ref relay eliminated (W1-#5 validated 2026-07-18: GitHub round-trips all three ref namespaces; sync needs no server) | when a second machine/person actually needs it |
| 5 | **Desktop** | Electron wrapper around the review SPA | when the SPA has proven what a GUI should be |
| 6 | **Online service / website** | hosted multi-tenant version of 3+4 (org dashboards, review/approval workflows, shared index, accounts) | product-stage; only if this becomes a product |

The online service, when/if it happens, is not a new system: it is surface 4 plus surface 3
behind auth. Keeping that identity is the architectural discipline that makes it cheap later.
